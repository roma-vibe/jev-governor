# Контекст: «убрано — не потеряно» и перенос в новый чат

План и механика. Идея: «история ≠ контекст». Она переложена на физику Claude Code: кэш промпта, сообщения хода нельзя
пересобирать, основная масса истории — выводы инструментов.

## Зачем (замеры на реальных сессиях, 17.09–05.10.2026)

| Показатель | Значение |
|---|---|
| Контекст одного запроса к модели, медиана | ~430k токенов (до ~966k) |
| Доля стоимости (по ценам API) | чтение кэша 61%, запись 24%, вывод 15% |
| Состав истории | результаты инструментов 89%, входы 9%, текст диалога 1,5% |
| «Скелет» сессии (запросы + итоговый ответ каждого хода) | медиана ~4k токенов, у самых больших 25–40k |
| «Сито устаревшего» (перечитанные файлы, повторные команды) | ~2% результатов — **не делаем** |

Вывод: главный рычаг — размер контекста, а не выбор модели. Его можно уменьшать
двумя способами: смелее сжимать текущий чат или переезжать в новый чат с
маленькой «капсулой» вместо 400k истории.

## Что не делаем и почему

- **Пересборка контекста на каждом сообщении.** API модов не даёт трогать
  сообщения хода (`turn.step`), и это сожгло бы кэш: на Opus запись в 40 раз
  дороже чтения.
- **Эмбеддинги, факты, пересказы реплик.** Они работают с текстом диалога, а это
  1,5% объёма. Для долговременных фактов в Claude Code уже есть CLAUDE.md и
  авто-память.
- **Сито устаревшего.** Замер дал ~2% — сложность не окупается.

## 1. Убрано — не потеряно (архив и ссылки при сжатии)

Сейчас сжатие через Jev выбрасывает старые вызовы инструментов, а от
результатов оставляет 300 символов и пометку «перезапусти инструмент».

Новая механика:

1. Перед возвратом сжатой истории каждый убранный вызов (вход и полный вывод)
   пишется в файл `outputs/<session>/pruned/<tool_use_id>.txt`. Действуют те же
   ограничения, что для обрезанных выводов: 7 дней и 200 МБ.
2. На месте урезанного результата появляется ссылка: начало вывода плюс
   `[jev-governor: … pruned; full output: <путь>]`.
3. Для вызовов, убранных целиком, ведётся список `pruned/index.md` (инструмент,
   аргумент, путь). Одна строка в сжатой истории указывает на этот список.
4. Чтение этих файлов разрешено без запроса (как обрезанные выводы) и пишется в
   журнал как `output-read`. По этим записям видно, как часто модели
   действительно нужно убранное. Это и есть метрика качества сжатия.

Эффект: сжатие перестаёт быть необратимым, поэтому пороги можно ставить
смелее, а включение режима active везде становится безопаснее.

## 2. Перенос сжатого контекста в новый чат

### Команды

- `/jevg getctx [фокус]` — в старом чате. Собирает капсулу, сохраняет её и копирует
  в буфер обмена короткий промпт для нового чата. Фокус необязателен: например,
  «продолжаем UI проектов». Флаги: `--brief` (бриф моделью всегда), `--nobrief`
  (без брифа).
- Новый чат того же проекта: вставить промпт из буфера. Мод в новом чате видит
  метку `jev-ctx:<id>` и прикрепляет капсулу к сообщению как скрытый контекст.
  Модель её читает, а в ленте её не видно. Если мод не активен, в промпте есть
  путь к файлу капсулы, и модель прочитает его сама.
- `/jevg ctx` — в новом чате без вставки: прикрепить последнюю капсулу проекта к
  следующему сообщению. `/jevg ctx list` — список капсул проекта,
  `/jevg ctx <id>` — конкретная капсула.

### Из чего состоит капсула (бюджет по умолчанию 14k токенов)

1. **Бриф** — пишет модель исходного чата: цель, состояние, решения и почему,
   отвергнутые варианты, открытые вопросы и следующий шаг, ключевые файлы и
   команды, подводные камни. Это единственная часть, которую механически не
   извлечь. Бриф делается только пока кэш исходного чата тёплый: это чтение
   кэша плюс ~1,5k токенов вывода, порядка $0.1 по ценам API на 400k
   контекста. На остывшем кэше тот же бриф стоил бы перезаписи всего контекста
   (~$3), поэтому по умолчанию он тогда пропускается.
2. **Ход работы** — запросы пользователя и итоговые ответы модели по ходам, по
   принципу «история ≠ контекст»: последние ходы целиком, более старые сжаты до сути, самые
   старые одной строкой. Какие старые ходы нужны для продолжения, решает Jev
   (вопрос «нужен ли этот ход для <фокус>»). Без Jev — по свежести.
3. **Файлы** — что создано и изменено (по вызовам Edit/Write), сколько раз.
   Содержимое не переносится: оно на диске.
4. **Последние проверки** — команды тестов и сборки и их итог («tests passed
   (59 passed, 0 failed)»).
5. **Где подробности** — путь к полному транскрипту старого чата и к архиву
   убранного.

### Почему старый чат не сжимается

В задумке было «сжать в оригинальном чате и отдать». Сжатие происходит, но не
на месте: капсула и есть сжатая версия. Сжимать сам старый чат перед уходом
бессмысленно — это оплата перезаписи кэша чата, который вы покидаете. Если
вы в нём останетесь, работают обычные правила сжатия.

### Экономика

Шаг в новом чате читает ~45k системного промпта и капсулу ~10k вместо 430k+
старой истории: на Opus это ~$0.011 вместо ~$0.086 за шаг. Бриф окупается за
2–3 шага нового чата.

## 3. Подсказка при смене темы

К вопросам Jev на каждом ходу добавлен `new_topic`: «запрос начинает новую
задачу, ранний разговор для неё не нужен». Если вероятность ≥ 0.8, а контекст
≥ 150k, мод показывает подсказку: «похоже, новая задача, контекст 380k —
дешевле продолжить с чистым чатом: `/jevg fresh`». Это только подсказка, не чаще раза в 10 ходов, и
она работает и в режиме наблюдения. Сам мод ничего не переключает: точность
определения темы 59–75%.

Подсказка «кэш остыл» с 0.2.6 выключена по умолчанию
(`handoff.suggestColdAtTokens` = 0): после паузы мод сначала сам сжимает чат
(`compaction.onReturn`), а 6 октября ни одна из трёх подсказок не пригодилась.

## Настройки (`config.json`)

- `compaction.archive` (true) — архив и ссылки при сжатии.
- `handoff.enabled` (true), `handoff.maxTokens` (14000),
  `handoff.brief` (`auto` | `always` | `never`), `handoff.briefWords` (350),
  `handoff.useJev` (true), `handoff.suggestAtTokens` (150000),
  `handoff.suggestAt` (0.8), `handoff.suggestColdAtTokens` (0, выключено),
  `handoff.keepDays` (30).
- `compaction.maxPruneRatio` (0.8) — больше этой доли истории одно сжатие не
  убирает; `compaction.resultPreviewChars` (150) — начало и конец каждого
  вывода, которые видит Jev.

## Как проверить, что это работает

- Журнал `compact`: поле `archived` — сколько вызовов ушло в архив.
- Журнал `output-read` с путями `pruned/` — модели понадобилось убранное. Если
  таких записей почти нет, сжатие можно делать смелее.
- Журнал `handoff`: размер капсулы против контекста старого чата, был ли бриф,
  прикрепилась ли капсула в новом чате.
- Журнал `hint`: как часто Jev видит смену темы на большом контексте.

- Журнал `rerun-after-prune`: модель снова запустила убранную команду или
  прочитала убранный файл. Вместе с чтениями `pruned/` это «обращений к
  убранному на одно сжатие» в отчёте `node scripts/monitor.mjs`.

## 4. `/jevg fresh`: перенос в том же окне

`/jevg fresh [--brief|--nobrief] [фокус]` собирает капсулу, как `getctx`,
затем выполняет `/clear` и подключает капсулу к следующему сообщению. Работа
продолжается в том же окне с контекстом ~14k. Если `/clear` не сработает,
промпт для нового чата остаётся в буфере обмена.

После `/clear` движок не присылает `session.start`: та же сессия процесса
получает новый id. Мод ловит это в `session.end` (`reason: clear`) и при
следующем хуке переходит на новый id. Раньше этого не было, и после `/clear`
журнал и состояние роутинга продолжали писаться в старую сессию.

Подсказка теперь называет `/jevg fresh` и показывается ещё в одном случае:
кэш контекста от 300k остыл (`handoff.suggestColdAtTokens`), и следующий ход
всё равно перезапишет его целиком.

Ещё не проверено в живом приложении: что `$.command.run({ command: 'clear' })`
доступен моду в приложении Claude (в тестах — на фейковом движке).

## 5. Пересечение со встроенными механизмами Claude Code (проверено 5 октября)

- **Большие выводы Bash.** Команда с выводом ~1 МБ: Claude Code сохранил его в
  файл `~/.claude/projects/<проект>/<сессия>/tool-results/<id>.txt`, а в
  историю (и в `session.append` мода) попало превью 2,3 КБ из начала вывода.
  Порог — около 30k символов (вывод 33 КБ тоже ушёл в файл). Значит:
  - `trim.hugeChars` (40k) для Bash не срабатывает никогда, обрезка видит
    Bash-выводы только до ~30k;
  - в превью нет конца вывода, то есть строк с ошибками и итога тестов.

  Уточнение (проверка той же ночью): в файл уходят только **успешные** прогоны.
  Команда с ошибкой (`seq 1 9000; exit 1`) пришла целиком в истории: «Exit
  code 1», начало и конец, середина вырезана; все 8 сохранённых выводов в
  транскриптах — с `is_error=false`. То есть строки с ошибками в упавшем
  прогоне и так видны.

  Что сделано: для успешных тестов, сборок и установок мод читает сохранённый
  файл и ставит на место превью короткую выжимку (итог, сводка, строки
  предупреждений, до ~3k без запросов к Jev), а не 16k лога. Файл берётся из
  записи движка о вызове (`persistedOutputPath`), а путь из текста превью —
  только если он в папке `tool-results` Claude Code: превью — это вывод
  команды, и команда может подделать в нём любой путь. Чтения этих файлов
  моделью журнал пишет как `output-read`. Команды, запущенные чтобы что-то
  прочитать (`cat`, `git diff`…), оставляют превью Claude Code. Порог
  `hugeChars` не менялся: он нужен для выводов других инструментов (MCP,
  WebFetch).
- **Microcompact на простое** (по данным поиска: с 2.1.284 старые результаты
  инструментов заменяются ссылками после ~65 минут простоя). Не проверено:
  нужен большой чат, оставленный на 70+ минут, и сравнение транскрипта до и
  после. Наше сжатие на простое срабатывает через 60 минут + 30 секунд, то есть
  раньше; если microcompact подтвердится, сравнить, кто что убирает, и решить,
  оставлять ли своё.

## 6. Сжатие посреди хода и в субагентах (0.2.6)

Анализ 6 октября (данные с 0.2.2, ≈ $96 по ценам API): субагенты стоили $42 из
$96 и росли с 29–44k до 300–480k за одну задачу (исследователи кода, читающие
файлы по 40–50 тыс. символов целиком), сжатий в субагентах — ноль. Один ход
основного чата тоже дважды вырастал с ~60k до 390–670k. Вывод у субагентов —
меньше 3% их цены: дорогой делает их контекст, а не effort.

Мод не может начать сжатие посреди хода: `$.session.compact` отказывает, пока
ход идёт, а сообщения в `turn.step` движка не меняются. Зато сам Claude Code
сжимает и посреди хода, и в субагентах, когда контекст доходит до окна
автосжатия, и наш хук `session.compact` прореживает такое сжатие через Jev, как
своё. Окно задаётся официальной переменной `CLAUDE_CODE_AUTO_COMPACT_WINDOW`.

- `compaction.autoWindowTokens` (250000; 0 — окно самого Claude Code): мод при
  старте сессии ставит эту переменную своему процессу через `$.env.set` и
  запоминает своё значение в `JEV_GOVERNOR_AUTO_WINDOW`. Переменную, заданную
  вами, мод не трогает; своё значение обновляет или снимает, когда настройка
  меняется.
- В журнале на каждую сессию одна запись `window`: что мод поставил и от чего
  на самом деле считает Claude Code (`tokens`, `source` = `env`, если
  переменная подействовала). Монитор сводит это строкой «Окно автосжатия».
- Сжатие, которое Claude Code начал на этом окне, записывается с причиной
  `window` (в субагенте — с его `agentId`) и в «Экономии» считается точно, как
  сжатие по порогу, в своём цикле: в субагенте — по его запросам и по цене
  5-минутной записи.
- Если Jev убирает меньше `minReductionRatio` (25%), остаётся пересказ Claude
  Code, как и раньше на пределе окна.

Грубая оценка по транскриптам 6 октября: окно 200–250k даёт основному чату
−25…30% стоимости контекста, субагентам −7…13%. Это верхняя оценка: проверить
по монитору после дня работы («Окно автосжатия», «сжатий в субагентах»,
«Контекст на шаг»). Если Claude Code не принял окно (`source` не `env`) или
субагенты так и не сжимаются, переменная на них не действует: тогда она нужна в
`env` файла `~/.claude/settings.json` (нужен новый процесс).
